# Платформа «ГириБро»: аккаунты, синхронизация и работа тренера

Черновик архитектуры для версий после `0.2.0`. Цель — не «добавить облако», а
дать тренеру возможность создавать тренировки и назначать их нескольким
спортсменам, а спортсмену — получать план и отчитываться о выполнении.

Статус: проектирование. Код платформы не начат. В `0.2.0` уже вышли локальные
функции, на которые будет опираться платформа: профиль спортсмена, черновик
тренировки, шифрованные резервные копии, автобэкап, напоминания и ярлыки
приложения. Аккаунты, синхронизация и тренерский режим отложены до оценки
востребованности.

## 1. Границы MVP

Входит:

- аккаунты по e-mail с одноразовым кодом (без паролей);
- синхронизация тренировок и замеров между устройствами;
- роль тренера в том же приложении (телефон/планшет);
- создание тренировки-шаблона и назначение её сразу нескольким спортсменам;
- спортсмен видит назначенный план, выполняет его, результат уходит тренеру;
- перенос назначения на другую дату с отметкой «перенесена»;
- результат «выполнено» или «есть нюансы» с комментарием;
- тренер видит выполнение и статистику своих спортсменов;
- согласие на передачу данных тренеру и отзыв доступа;
- удаление аккаунта и экспорт данных внутри приложения.

Не входит в MVP:

- веб-кабинет тренера;
- публичная лента, клубы и комментарии;
- чат;
- оплата и подписки (нужен ИП/юрлицо, пока не готовы);
- push-уведомления (обновление данных при открытии приложения);
- загрузка фото и видео;
- отчёты и выгрузки для тренера (CSV/PDF);
- автоматические программы тренировок и ИИ-рекомендации.

## 2. Роли и сценарии

Один пользователь может быть и тренером, и спортсменом. Роль — не эксклюзивная,
это набор возможностей.

### Тренер

1. Регистрируется, указывает имя.
2. Создаёт группу или просто выбирает спортсменов из списка.
3. Приглашает спортсмена кодом или ссылкой.
4. Создаёт тренировку в конструкторе: упражнения, подходы, вес, повторы, время,
   отдых, заметка.
5. Сохраняет её как шаблон.
6. Назначает шаблон одному, нескольким или всей группе на дату (или без даты).
7. Открывает «Мои спортсмены»: кто выполнил, тоннаж за неделю, последняя
   тренировка, комментарий.
8. Может отредактировать будущее назначение; уже выполненные не меняются.

### Спортсмен

1. Регистрируется или принимает приглашение тренера.
2. Видит назначенные тренировки в дневнике.
3. Открывает назначение — конструктор уже заполнен планом тренера.
4. Может скорректировать вес/повторы под себя, выполнить и сохранить.
5. Если не получается — переносит назначение на другую дату; оно помечается
   «перенесена», у тренера видна исходная дата.
6. При сохранении выбирает результат: «Выполнено» или «Есть нюансы» и пишет
   комментарий.
7. Видит свои обычные тренировки и статистику; назначенные помечены.
8. Управляет доступом: тренер видит тренировки, замеры тела — только если
   включено отдельно.
9. Может отозвать доступ тренера и удалить аккаунт.

## 3. Модель данных

Все идентификаторы — UUID, генерируются на клиенте. Это нужно для офлайн-работы
и синхронизации: два устройства не создадут одинаковых ID.

### Сервер (Postgres)

```text
users
  id uuid pk
  email citext unique
  name text
  created_at timestamptz
  deleted_at timestamptz null
  share_measurements bool default false

auth_codes
  email citext
  code_hash text
  expires_at timestamptz
  attempts int
  created_at timestamptz

sessions
  id uuid pk
  user_id uuid fk
  refresh_hash text
  device_name text
  created_at timestamptz
  last_seen_at timestamptz
  revoked_at timestamptz null

coach_athletes
  coach_id uuid fk users
  athlete_id uuid fk users
  status text            -- invited | active | revoked
  created_at timestamptz
  revoked_at timestamptz null

groups
  id uuid pk
  coach_id uuid fk
  name text
  created_at timestamptz
  deleted_at timestamptz null

group_members
  group_id uuid fk
  athlete_id uuid fk
  created_at timestamptz

templates
  id uuid pk
  coach_id uuid fk
  title text
  note text
  payload jsonb          -- секции и подходы в формате дневника
  created_at timestamptz
  updated_at timestamptz
  deleted_at timestamptz null

assignments
  id uuid pk
  coach_id uuid fk
  athlete_id uuid fk
  template_id uuid null
  title text
  scheduled_date date null
  original_date date null   -- исходная дата до первого переноса
  rescheduled_at timestamptz null
  reschedule_count int default 0
  payload jsonb          -- снимок плана на момент назначения
  status text            -- assigned | rescheduled | completed | completed_with_issues
  athlete_note text null -- комментарий к результату или переносу
  created_at timestamptz
  updated_at timestamptz
  deleted_at timestamptz null

workouts
  id uuid pk
  athlete_id uuid fk
  assignment_id uuid null
  performed_at date
  payload jsonb
  created_at timestamptz
  updated_at timestamptz
  deleted_at timestamptz null

body_measurements
  id uuid pk
  athlete_id uuid fk
  measured_at date
  payload jsonb
  created_at timestamptz
  updated_at timestamptz
  deleted_at timestamptz null
```

Ключевое решение: **назначение хранит снимок плана** (`payload`), а не ссылку на
шаблон. Тренер может менять шаблон сколько угодно — у спортсмена останется то,
что ему назначили. Это же снимает конфликты синхронизации.

`payload` переиспользует текущий JSON-формат секций из `WorkoutEntity` и
`DiaryBackup` — новый формат придумывать не нужно.

### Статусы назначения

| Статус | Кто ставит | Что означает |
| --- | --- | --- |
| `assigned` | тренер | назначено на дату |
| `rescheduled` | спортсмен | перенесено: `scheduled_date` — новая дата, `original_date` — исходная |
| `completed` | спортсмен | выполнено по плану, создана связанная тренировка |
| `completed_with_issues` | спортсмен | выполнено с нюансами, `athlete_note` обязателен |

Перенос не требует подтверждения тренера. При повторном переносе
`original_date` не меняется, `reschedule_count` увеличивается. Тренер видит
бейдж «перенесена» и исходную дату. Статус «есть нюансы» тоже показывается
бейджем, комментарий спортсмена виден в карточке назначения.

Назначение нескольким спортсменам — одна операция, создающая N записей
`assignments` с одинаковым `payload`. Группа — просто сохранённый набор
спортсменов, чтобы не выбирать их каждый раз.

### Клиент (Room, версия 3)

Новые/изменённые таблицы:

- `workouts`: `id` → UUID-строка, добавить `updated_at`, `deleted_at`,
  `assignment_id`, `server_updated_at`;
- `body_measurements`: то же;
- `templates`, `assignments`, `coach_athletes`, `groups` — кэш серверных данных;
- `sync_state`: последний полученный курсор.

Миграция 2→3: создать новые таблицы, перенести старые строки, сгенерировать UUID
для существующих тренировок и замеров, сохранить старые `Long` во временной
колонке до подтверждения миграции. Старые резервные копии v1/v2 продолжают
читаться.

## 4. Синхронизация

Офлайн-first: любое действие сначала пишется в Room и попадает в очередь, затем
отправляется на сервер.

- Push: клиент отправляет пачку изменений с `client_id` (UUID операции) для
  идемпотентности. Сервер отвечает `server_updated_at` для каждой записи.
- Pull: `GET /sync?since=<cursor>` возвращает изменённые записи и tombstones
  (`deleted_at`), курсор — монотонный серверный счётчик.
- Конфликты: last-write-wins по `updated_at`, но только для личных тренировок и
  замеров. Назначения и шаблоны тренера — серверные сущности, спортсмен их не
  редактирует, поэтому конфликтов нет.
- Удаление: мягкое (`deleted_at`), физическая чистка на сервере по расписанию.
- Фон: WorkManager при открытии приложения, после сохранения, раз в несколько
  часов. Push-уведомления в MVP не нужны.

Ограничение MVP: синхронизация запускается вручную/по событию, а не в реальном
времени. Тренер видит результат, когда спортсмен открыл приложение и отправил
изменения, либо когда тренер потянул обновление.

## 5. API (черновик)

```text
POST   /v1/auth/request-code        {email}
POST   /v1/auth/verify              {email, code} -> access, refresh
POST   /v1/auth/refresh             {refresh}
POST   /v1/auth/logout

GET    /v1/me
PATCH  /v1/me                       {name, share_measurements}
DELETE /v1/me                       удаление аккаунта и всех данных
GET    /v1/me/export                JSON-экспорт

POST   /v1/invites                  -> код (многоразовый, срок 7 дней)
POST   /v1/invites/accept           {code}
GET    /v1/coach/athletes
PATCH  /v1/coach/athletes/{id}      {status: revoked}
GET    /v1/coach/athletes/{id}/stats?from&to

GET    /v1/coach/groups
POST   /v1/coach/groups             {name, athlete_ids[]}
PATCH  /v1/coach/groups/{id}
DELETE /v1/coach/groups/{id}

GET    /v1/coach/templates
POST   /v1/coach/templates          {title, note, payload}
PATCH  /v1/coach/templates/{id}
DELETE /v1/coach/templates/{id}

POST   /v1/coach/assignments        {template_id, athlete_ids[], scheduled_date?}
GET    /v1/coach/assignments?from&to
PATCH  /v1/coach/assignments/{id}
DELETE /v1/coach/assignments/{id}

GET    /v1/athlete/assignments?since
PATCH  /v1/athlete/assignments/{id} {scheduled_date}          -- перенос
POST   /v1/athlete/assignments/{id}/complete {workout, status, note?}
POST   /v1/athlete/workouts         {workout}                 -- обычная тренировка
GET    /v1/sync?since=<cursor>
```

Все ответы тренера проверяют связь `coach_athletes.status = active` на сервере.
Клиентская проверка — только для UI, не для безопасности.

## 6. Приватность и доступ

- Тренер видит тренировки спортсмена только при активной связи.
- Замеры тела по умолчанию **скрыты**; спортсмен включает их отдельным
  переключателем. Это должно быть явно написано на экране приглашения.
- Отзыв доступа мгновенно скрывает данные у тренера, но не удаляет их у
  спортсмена.
- Удаление аккаунта: каскадно удаляет тренировки, замеры, назначения, связи;
  тренер теряет доступ.
- Экспорт — тот же JSON, что и локальная резервная копия.
- На сервере — шифрование диска и бэкапов, TLS, минимальные логи без ПДн.

## 7. Экраны

Тренер (телефон/планшет):

- «Мои спортсмены»: список, статус, последняя тренировка, выполнение за неделю;
- карточка спортсмена: статистика, история, доступ к замерам;
- бейджи «перенесена» и «есть нюансы», комментарий спортсмена;
- «Планы»: список шаблонов, создание из конструктора;
- «Назначить»: выбор шаблона → выбор спортсменов/группы → дата → подтверждение;
- «Пригласить»: код и системное «Поделиться».

Спортсмен:

- в дневнике — блок «Назначено тренером»;
- открытие назначения в конструкторе с предзаполненными подходами;
- действия «Выполнено», «Есть нюансы» (с комментарием), «Перенести»;
- экран «Тренер»: кто тренер, что видит, отзыв доступа;
- настройки: аккаунт, синхронизация, экспорт, удаление.

## 8. Этапы и оценка

| Этап | Содержание | Оценка |
| --- | --- | --- |
| 0 | Дождаться модерации 0.2.0, подготовить юридику | 1–2 недели ожидания |
| 1 | Backend: auth, БД, деплой, CI, бэкапы | 1,5–2 недели |
| 2 | Клиент: вход, токены, миграция Room, sync тренировок и замеров | 2–3 недели |
| 3 | Тренер: шаблоны, назначение нескольким, экран спортсменов | 2–3 недели |
| 4 | Приватность, удаление аккаунта, экспорт, тесты | 1–2 недели |
| 5 | Пилот с тренером, исправления, релиз 0.3.0 | 2 недели |

Итого: около **8–10 недель** соло, без веб-кабинета и комьюнити. Инфраструктура:
VPS в РФ 2 vCPU / 4 ГБ + Postgres + бэкапы — примерно 1–2 тыс. ₽/мес; SMTP для
кодов входа — от бесплатного до пары сотен рублей.

## 9. Пилот

- 1 тренер, 5–10 спортсменов, 4 недели.
- Метрики: сколько назначений создано, доля выполненных, сколько спортсменов
  вернулось на второй неделе, сколько раз тренер открыл статистику.
- Главный вопрос пилота: экономит ли это тренеру время по сравнению с
  мессенджером. Если нет — фича не нужна, и это лучше узнать до комьюнити.

## 10. Юридика и RuStore

- 152-ФЗ применяется и без ИП: физлицо тоже может быть оператором ПДн. Нужны
  уведомление Роскомнадзора, политика, согласие, удаление и экспорт.
- Данные о здоровье — специальная категория, поэтому согласие на передачу
  тренеру должно быть отдельным и отзываемым.
- Политику конфиденциальности придётся переписать: сейчас она утверждает, что
  данные не покидают устройство.
- Декларация RuStore изменится: личные данные, здоровье, сеть, аккаунты.
- Монетизация откладывается: RuStore Pay для физлиц недоступен, нужен ИП/ООО.
  В MVP не закладываем платежи, но модель данных не должна им мешать.
- Публичное комьюнити потребует модерации UGC и правил — отдельный этап.

## 11. Открытые вопросы

1. Код приглашения: многоразовый на 7 дней — удобно для группы, но менее
   безопасно. Оставляем так или делать одноразовый на спортсмена?
2. Перенос: ограничить, например, тремя переносами или разрешить сколько
   угодно?
3. «Есть нюансы»: комментарий обязателен — подтверждаете?
4. Нужен ли отдельный статус «пропущено», если спортсмен не выполнил и не
   перенёс?
5. Нужно ли тренеру видеть, что спортсмен открыл назначение?
